# Export-byte rebaseline — 2026-09-02

Why `public/data/posts.json` and `public/data/manifest.json` changed hash without any value
changing, and where the +228 bytes came from. Written so this is never re-discovered as
"unexplained drift".

## What happened

A normal deploy (`npm run deploy:web`, **no `SKIP_EXPORT`**) ran a full Firestore export. The
export completed successfully — 8.09 MB bundle, every certified QA check passing — and then
`deploy-web.sh` refused to publish, because the export had changed two tracked files:

```
!! DEPLOY BLOCKED — the Firestore export changed 2 tracked file(s).
 M public/data/manifest.json
 M public/data/posts.json
```

**Nothing was published.** The refusal is the gate working: bytes that were not the validated
bytes cannot be stamped by `write-build-info.mjs`, so it stops before the build rather than four
minutes later.

## The two differences

### 1. `posts.json` — one row, property order only

| | |
|---|---|
| documents | 4,966 both sides, none added, none removed |
| row order | identical, position by position |
| byte length | **10,400,391 both sides** |
| rows differing by value | **0** |
| rows differing by key order | **1 — post #4686** |
| whole-file semantic hash | **identical** |

The single ordering difference, at `posts[#4686].postAnalysis`:

```
committed    … claimSpans, contextUnits, predictionSpans
regenerated  … claimSpans, predictionSpans, contextUnits
```

`contextUnits` and `predictionSpans` are appended by different steps of the apply chain. #4686 is
the drop that gained a Prediction under the "WATERGATE x1000" ruling, so it is the only row where
both keys were appended in the same run and their relative order can differ between the rebuild
path and the export path.

This is confirmed independently by the certification manifest, which carries **two** hashes per
artifact: `sha256` over the raw bytes and `semanticSha256` over the content with keys sorted.
Across the rebaseline the semantic hash of `posts.json` is unchanged —
`1f17fd924d5444b701a4e65417dca7098bde47c3bbfab04f24196212232c3501` — while only the raw hash
moved. `certification-manifest.mjs --verify` classifies that as re-serialisation, not a content
change, which is why it passed both before and after.

### 2. `manifest.json` — a stale aggregate, corrected

`totalBytes` 12,340,347 → **12,340,575**, delta **+228**. Nothing else in the file changed; the
`collections` block is byte-identical.

The +228 reconciles exactly, and both halves are verifiable from git:

```
posts.json at 7f73af5  (pre-#4686, seed 116)   10,400,163 bytes
posts.json at 224ef91  (#4686 ruled)           10,400,391 bytes
                                        delta      +228

manifest.totalBytes at 7f73af5                 12,340,347
manifest.totalBytes at 224ef91                 12,340,347   ← not recomputed
manifest.totalBytes regenerated by the export  12,340,575
                                        delta      +228
```

**The manifest was stale, not the export.** Commit `224ef91` added "WATERGATE x1000" to #4686,
which grew `posts.json` by 228 bytes, but `manifest.totalBytes` was carried forward unchanged from
the pre-ruling bundle. It stayed wrong through `9136952` — the build that is live — because the
2026-09-02 deploy shipped under `SKIP_EXPORT=1` and never recomputed it. The first ordinary export
since then corrected it.

`manifest.collections.posts.bytes` (6,545,584) is **not** the published file size and was not
touched. It is the raw Firestore collection dump, which the exporter subtracts out before adding
the final enriched file:

```js
manifest.totalBytes = statSync(join(outDir, 'posts.json')).size + grandBytes
  - manifest.collections.posts.bytes
```

## Determinism, proved before committing

The preserved export bytes were installed and the local generation chain run **twice**:

- both runs exit 0, and their output is identical
- `posts.json` stays at `69d345ec96f1887f062cb00d50b87d903c0776bfd9c8e3b8af548d9bf9ce3491`
- `manifest.json` stays at `603b68a612d9a5a8f2e02a0a583446294ea41ef28b5ecdb7ac319281acf7f355`

So the chain reproduces the export's serialisation rather than fighting it. Had it drifted, that
would have meant serialisation is still non-deterministic and the rebaseline would have been wrong
to commit.

## What was refreshed, and what was not

- `audit/certification-manifest.json` — regenerated through its own generator, never hand-edited.
  Exactly two fields moved: `certifiedAt`, and `artifacts["posts.json"].sha256`. Every count, the
  `canonical` block, `seedVersion`, and every `semanticSha256` are unchanged. The generator refuses
  to write at all if a canonical count has drifted, so the fact that it wrote is itself evidence.
- Cross-section audit re-run with all three private editorial queues present: **222/222, 0 skipped**.
- `SEED_VERSION` unchanged at **117**. #4686 still carries "WATERGATE x1000" as a Prediction. The
  picture audit still holds 1,690 records — 1,653 complete, 29 partial, 8 content-filter withholds.

## The gap this exposed

`totalBytes` was wrong for two deploys and **no gate noticed**, including a clean 38-step FULL
validation. It was found only by spending a real export during a deployment. Nothing in `scripts/`
recomputes `public/data/manifest.json`'s byte accounting through the same function the exporter
uses. Recorded as a follow-up, not fixed here.
